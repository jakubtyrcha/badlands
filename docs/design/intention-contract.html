The Intention Contract

brain ⇄ engine wire v3 — canonical design doc, Slice B (feat/intention-contract)

Diagram-rich successor to docs/superpowers/specs/2026-07-24-intention-contract-design.md (the prose spec) and docs/superpowers/specs/2026-07-25-contract-v3-alignment-design.md (the v3 amendment's own spec). Where they overlap, the three must agree on every name and rule; this page exists to make the shape of the contract legible at a glance, not to replace either spec's reasoning.

Shipped 2026-07-29: contract v3 has landed — the running binary is BL_ABI_VERSION 3. Cadence, resume/restate, bl_enqueue_action, and BL_ACT_ATTACK are all live; unmarked text below now describes that shipped v3 behavior exactly. What still carries a v3 badge is the one part that did NOT ship this slice: BL_ACT_USE_SKILL/BL_ACT_USE_POTION (and the BL_INT_USE_SKILL intention kind they supersede) remain reserved for the skills slice.

An agent has exactly one brain call per wake. The brain reads a snapshot of the world (state) plus whatever happened since it last looked (events), and returns exactly one suggestion: an intention, an activity label, and an idleness hint. The engine — never the brain — decides whether to execute it, executes it by turning it into a logged Command, and the world moves on. The brain finds out how things went later, if at all, the same way it finds out anything: via state and events on its next wake.

Who this contract governs

This contract governs agents: AI complex enough to hold goals, react to events, and reconsider. The tier test: does it need memory, goals, or reconsideration? No → simple tier, plain engine code by design, no brain call at all — tax collectors and peasants are dumb enough not to flee; deer are pure reaction, no goals. Heroes are the first contract-driven agents; most enemies — a goblin warband holding a goal, say — are the intended next tier to join.

The view splits conceptually into a common envelope every agent kind shares (vitals, statuses, the event inbox, a current-intention summary) plus a per-agent-kind perception profile layered on top — today that's the hero suggest block (§3). A monster profile arrives with the first non-hero agent kind: out of scope for this amendment, expected alongside or after v3.

Names this contract pins (later tasks implement these verbatim)

CurrentIntention
Durable per-agent engine state: the intention being executed right now (if any), since when, and how it maps onto the command/movement machinery. Outlives a single tick; read by should_wake, written by apply_intention.
EventInbox
Durable per-agent engine state: a bounded, sticky ring of timed events written by engine systems (combat, movement, the intention executor). Survives across sleep; entries expire on their own TTL, not on being read.
apply_intention
Engine function: commits a validated suggestion onto the command/movement machinery. The accepted intention is the logged Command — event-sourced, same as every other mutation in this codebase.
should_wake
Engine function: a per-tick, per-agent predicate. Returns whether react() runs for this agent this tick. Reads only durable, replayable state — never the brain.

1The loop

One brain wake is one trip around this ring. The brain owns exactly one box (react()); the engine owns the rest.

Two kinds of output

One wake's inside is a small loop body, not a single return: wake → optionally enqueue any number of actions via the write-only host import bl_enqueue_action(kind, target, arg) (instant, non-blocking — appended straight to the engine's resolve list for this tick) → always yield exactly one suggestion, same shape as v2's.

INTENTION
A long-lasting goal — go there, fight that. Owns CurrentIntention, has a lifecycle, ends with an IntentionEnded event. Unchanged shape from v2.
ACTION
An instant spike — use a skill, drink a potion, a concrete attack pick. Fire-and-forget: enqueued via bl_enqueue_action, resolved this tick, never touches CurrentIntention. Only BL_ACT_ATTACK is live; v3 USE_SKILL/USE_POTION remain reserved for the skills slice (§5).

The agent restates its current intention on every wake, whether or not anything should change — the engine diffs the restatement against CurrentIntention: identical = resume (edge-triggered, nothing new logged), changed = validated and adopted, same acceptance rule as always.

This is the single gateway combat runs through too: there is no separate host-level combat pass anymore. Attacking is exactly one more ACTION, enqueued via this same bl_enqueue_action channel every other action uses — whether the acting brain is the wasm hero contract or a simple in-engine brain (a rat, a goblin). The tier test (above, "Who this contract governs") only decides WHERE a brain runs; it never opens a second door into combat.

react() never learns the outcome of its own suggestion in the same call — only later, via the next wake's state + events (e.g. an INTENTION_ENDED event, a changed health_frac). Same story for enqueued actions: their outcome isn't visible in the call that enqueued them either — only later, via state/events on a subsequent wake.

Validation is the engine's alone: an accepted suggestion is feasible right now (e.g. its target_slot still names a real, reachable entity). An infeasible one is logged and dropped — the agent's CurrentIntention is untouched, so it either keeps doing what it was already doing or falls back to idling. The brain is advisory; it is never authoritative over what actually happens. Enqueued actions get the same validate-or-drop treatment, and it happens at resolve time, per action — not at enqueue. bl_enqueue_action is write-only and always "succeeds" from the agent's side; the engine validates each action against the world as it stands when that action resolves. An action on cooldown, naming a dead target, or spending a resource the agent no longer has is warned and dropped — and because actions resolve in enqueue order, an earlier action in the same wake can invalidate a later one (the first USE_SKILL starts the cooldown that rejects a duplicate second). Each action is judged independently: one drop never cancels the rest of the batch or the yielded intention. The agent learns the outcome the same way it learns everything — from state and events on a later wake — never from a return value. Actions never touch CurrentIntention either way; only an adopted intention does that.

Action resolution

Actions resolve in enqueue order, within the wake's own tick — and, the one ordering rule that actually matters, after this wake's intention diff has landed: apply_intention validates/adopts (or resumes) the yielded suggestion first, then the drained bl_enqueue_action calls resolve through the action resolver, in call order. This is what lets an action naming UINT32_MAX (BL_ACT_ATTACK's "whatever I'm already engaged with") resolve against a CurrentIntention that already reflects THIS wake's Attack adoption — including the very first wake that adopts Attack and swings in the same breath.

Soft convention, not an API rule: most agents should enqueue at most one action and then yield immediately. The API permits more per wake (a boss with several readied abilities, say) — nothing stops it, but restraint is the expectation.

Rejected for the record: generator-style multi-yield — re-invoking think() repeatedly within a wake until it signals "done." Rejected for costing multiple host↔guest calls per wake, guest-side reentry state to track between them, and being the worst fit of the options considered for a boundary meant to stay swappable — an LLM standing in for react() cannot be resumed mid-turn the way a plain function can.

2Wakeup state machine

The brain is consulted sparsely — that sparseness is the point of the interface (it's what makes the boundary swappable for an LLM or a neural net later: you do not call one of those 30×/second). Every tick, should_wake decides, per agent, whether react() runs at all.

Spurious wakeups are allowed at any tick — a brain woken for no listed reason must still re-decide idempotently (re-suggesting the same intention is a valid answer). Bypass statuses skip the think entirely: the mechanism drawn above exists from v1, but no v1 status (BL_ST_CHATTING/MELEE_LOCKED/INSIDE_BUILDING) actually sets it — all three are advisory only this slice. The first status that bypasses thinking is an implementation detail of a future slice. Separately, an InsideBuilding agent is skipped by the per-agent brain loop outright (a component-exclusion in the loop itself, before should_wake is ever consulted) — a bypass by exclusion, not the status-bypass mechanism this diagram draws. "No CurrentIntention" (top of the reasons box) is not an unconditional wake, either: a rejected or no-op (BL_INT_NONE) suggestion arms a short backoff on the same wake_at_millis field an idle hint uses, so an agent whose brain keeps declining is re-consulted at a bounded rate instead of every tick — the bullet means "no intention running and no such backoff pending."

Tiered wake guarantees

High-stakes (a threat in view, or in combat): the engine offers a consult every tick while the threat is present — the agent may assume per-tick cadence, but this is an engine offer, not an agent obligation. A slow implementation (an LLM, say) may answer less often; the engine stays authoritative over what actually executes either way, same as always (§1). This is what combat runs on: a wasm hero with a threat in view (or locked in melee) is consulted every tick for as long as the fight lasts — engagement (the Attack intention's approach) and swings (BL_ACT_ATTACK) both arrive through this one per-tick wake, at the same cadence a dedicated combat pass would have run at. The simple in-engine brains (rats, goblins) need no wake gate at all — engine code is cheap, so they are consulted unconditionally, every tick — but issue through these exact same seams, never a privileged one.

Normal (everything else): guaranteed at least once per second of 1x sim time. No hint (idle_hint_millis 0) means "no preference" and defaults the next wake to last_think_millis + 1s; any positive hint — shorter or longer than 1s — is honored as given. An explicit longer yield — "sleep 4 hours" — is honored, unless a guaranteed-wake event fires first (the list above is unchanged).

Semantics: idle_hint_millis == 0 means "no preference," and the 1s default cadence (kDefaultWakeCadenceMillis) applies. This replaces v2's old rule, where 0 meant idle-until-woken with no default cadence to fall back on. Rationale: the review found a class of stuck-forever-with-hint-0 defects; a structural default cadence deletes that class rather than relying on every producer to remember to set a hint.

Resume-by-default

Agents operate on a resume assumption: unless events or state actively warrant a change, an agent keeps doing what it was already doing. A wake — spurious or not — never cancels a running CurrentIntention on its own; a spurious wakeup that re-suggests the same thing loses nothing. Events are inputs to reconsideration, not resets.

This already held in spirit back in v2: the spurious-wakeup note above — re-suggesting the same intention is always a valid, free answer — is the same property. What v3 shipped is the mechanics: the engine recognizes an identical restatement as an edge-triggered resume that doesn't re-log a Command (§1), and the action channel (§1) lets a resumed intention still do something new this tick.

Worked example: a hero mid-Attack (engaged with whatever select_target currently finds nearest) gets a combat-tick wake. It yields the same intention — Attack, actor-only, a resume — and enqueues BL_ACT_ATTACK(target, arg) naming that enemy's slot and its best ready attack. The swing fires without disturbing the engagement: the intention keeps running exactly as it was (still chasing whichever enemy is nearest, not a stored target), the action is a one-off spike layered on top.

3Wire layout — BL_ABI_VERSION 3

v2 (still the bulk of the shape below) was a wholesale redesign of game/src/brain_abi.h / scripts/brains/nim/abi.nim: every BL_CMD_* became BL_INT_* — the brain suggests an intention now, not a command — and the view gained two blocks: statuses and events. v3 adds one more: attacks, sitting right after statuses (below) — a brain cannot pick an attack it cannot see. Same layout discipline throughout: every struct lists its int64_t fields first, every alignment pad is explicit (never left to the compiler), and buffer addresses are queried once at instantiation and fixed for the instance's lifetime.

BlViewWire (in) — block order

Block order and names are binding (self / suggest / factors / statuses / attacks / events / chars). Exact per-field byte offsets inside self/suggest/factors/chars are finalized in the implementing task — this shows the shape and the layout discipline, not final offsets.

4Event-inbox lifecycle

EventInbox is engine-written, bounded, and sticky: a sleeping agent does not miss what happened while it slept. An entry survives until it is read at some wake, or until its own TTL runs out first — whichever comes first isn't actually a choice the entry makes; expiry is purely time-based, so an agent that never wakes before the TTL elapses loses the entry unread.

v1 kinds: BL_EV_DAMAGE_TAKEN, BL_EV_THREAT_SIGHTED, BL_EV_MOVE_BLOCKED, BL_EV_INTENTION_ENDED. All four are guaranteed-wake events (§2).

6Determinism

state = f(initial config, command log, N ticks) must hold exactly as it does today. Nothing about replay changes — only which systems produce the log changes.

The idle hint rides inside the logged Command's payload — the same place today's deliberation-pause duration already lives. It is recorded once, at decision time, never recomputed. Replay never calls apply_intention — only react()'s live caller does that. It re-applies each logged Command through the ordinary apply_command mutation point instead (the SetBehavior handler derives wake_at_millis from the command's payload, and every per-kind command — MoveTo, Attack, EnterBuilding, ... — replays its own world mutation the same way any other command does). CurrentIntention.kind/point/target_slot/arg are stamped only inside apply_intention itself, so they stay None/default on a replayed world; the replayed command stream still reproduces the same observable positions, hp, and building occupancy, since those come from the per-kind commands, not from CurrentIntention. should_wake's outcome need not be re-evaluated as a wasm call either way — the wake schedule is already baked into the log. The same is true of actions: the action resolver is never called on replay either — a replayed Attack command's swing, explicit attack index (param_a) included, comes from the log exactly like every other command, not from a live BL_ACT_ATTACK re-resolution. This is what makes a whole fight replay bit-identically from the log alone, with no brain and no resolver running at all — engagement (CommandKind::Engage) and every swing are both logged commands now, closing the gap where combat used to be the one thing no suite actually replayed.
