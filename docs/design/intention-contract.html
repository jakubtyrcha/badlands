The Intention Contract

brain ⇄ engine wire v2 — canonical design doc, Slice B (feat/intention-contract)

Diagram-rich successor to docs/superpowers/specs/2026-07-24-intention-contract-design.md (the prose spec). Where they overlap, the two must agree on every name and rule; this page exists to make the shape of the contract legible at a glance, not to replace the spec's reasoning.

A hero has exactly one brain call per wake. The brain reads a snapshot of the world (state) plus whatever happened since it last looked (events), and returns exactly one suggestion: an intention, an activity label, and an idleness hint. The engine — never the brain — decides whether to execute it, executes it by turning it into a logged Command, and the world moves on. The brain finds out how things went later, if at all, the same way it finds out anything: via state and events on its next wake.

Names this contract pins (later tasks implement these verbatim)

CurrentIntention
Durable per-hero engine state: the intention being executed right now (if any), since when, and how it maps onto the command/movement machinery. Outlives a single tick; read by should_wake, written by apply_intention.
EventInbox
Durable per-hero engine state: a bounded, sticky ring of timed events written by engine systems (combat, movement, the intention executor). Survives across sleep; entries expire on their own TTL, not on being read.
apply_intention
Engine function: commits a validated suggestion onto the command/movement machinery. The accepted intention is the logged Command — event-sourced, same as every other mutation in this codebase.
should_wake
Engine function: a per-tick, per-hero predicate. Returns whether react() runs for this hero this tick. Reads only durable, replayable state — never the brain.

1The loop

One brain wake is one trip around this ring. The brain owns exactly one box (react()); the engine owns the rest.

react() never learns the outcome of its own suggestion in the same call — only later, via the next wake's state + events (e.g. an INTENTION_ENDED event, a changed health_frac).

Validation is the engine's alone: an accepted suggestion is feasible right now (e.g. its target_slot still names a real, reachable entity). An infeasible one is logged and dropped — the hero's CurrentIntention is untouched, so it either keeps doing what it was already doing or falls back to idling. The brain is advisory; it is never authoritative over what actually happens.

2Wakeup state machine

The brain is consulted sparsely — that sparseness is the point of the interface (it's what makes the boundary swappable for an LLM or a neural net later: you do not call one of those 30×/second). Every tick, should_wake decides, per hero, whether react() runs at all.

Spurious wakeups are allowed at any tick — a brain woken for no listed reason must still re-decide idempotently (re-suggesting the same intention is a valid answer). Bypass statuses skip the think entirely: the mechanism exists from v1, but no v1 status (BL_ST_CHATTING/MELEE_LOCKED/INSIDE_BUILDING) actually sets it — all three are advisory only this slice. The first status that bypasses thinking is an implementation detail of a future slice.

3Wire layout — BL_ABI_VERSION 2

Wholesale redesign of game/src/brain_abi.h / scripts/brains/nim/abi.nim. Every BL_CMD_* becomes BL_INT_* — the brain suggests an intention now, not a command — and the view gains two blocks: statuses and events. Same layout discipline as v1: every struct lists its int64_t fields first, every alignment pad is explicit (never left to the compiler), and buffer addresses are queried once at instantiation and fixed for the instance's lifetime.

Block order and names are binding (self / suggest / factors / statuses / events / chars). Exact per-field byte offsets inside self/suggest/factors/chars are finalized in the implementing task — this shows the shape and the layout discipline, not final offsets.

4Event-inbox lifecycle

EventInbox is engine-written, bounded, and sticky: a sleeping hero does not miss what happened while it slept. An entry survives until it is read at some wake, or until its own TTL runs out first — whichever comes first isn't actually a choice the entry makes; expiry is purely time-based, so a hero that never wakes before the TTL elapses loses the entry unread.

v1 kinds: BL_EV_DAMAGE_TAKEN, BL_EV_THREAT_SIGHTED, BL_EV_MOVE_BLOCKED, BL_EV_INTENTION_ENDED. All four are guaranteed-wake events (§2).

6Determinism

state = f(initial config, command log, N ticks) must hold exactly as it does today. Nothing about replay changes — only which systems produce the log changes.

The idle hint rides inside the logged Command's payload — the same place today's deliberation-pause duration already lives. It is recorded once, at decision time, never recomputed. Replay re-applies the logged Command and lets the same deterministic engine systems run; it never calls react(), so should_wake's outcome need not even be re-evaluated as a wasm call — the wake schedule is already baked into the log.
